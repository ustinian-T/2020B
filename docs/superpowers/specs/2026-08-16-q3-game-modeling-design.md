# 第三问多人博弈求解代码设计

## 目标与范围

依据《第三问建模手册_完整详细版_含模型检验与灵敏度分析》，在
`求解代码/第三问（1）` 与 `求解代码/第三问（2）` 内分别实现第五关和第六关的
Python 求解、模型检验、灵敏度分析及结构化结果导出代码。

本次包含可执行求解代码、自动化测试、CSV/JSON 输出和模型检验；不包含 MATLAB、
Python 绘图代码，不生成图片，也不改动建模手册、论文或第一、第二问代码。

## 全局规则

- 第五关：2 名玩家、10 天、起点 1、矿山 9、终点 13、无村庄；天气固定为
  `晴朗、高温、晴朗、晴朗、晴朗、晴朗、高温、高温、高温、高温`。
- 第六关：3 名玩家、30 天、起点 1、村庄 14、矿山 18、终点 25；策略每天仅接收
  当前天气和公开状态，不能接收或读取未来真实天气。
- 两关均采用 1200 kg 负重、10000 元初始资金；水每箱 3 kg/5 元，食物每箱
  2 kg/10 元；基础消耗为晴朗 `(3,4)`、高温 `(9,9)`、沙暴 `(10,10)`。
- 普通停留消耗 1 倍，挖矿消耗 3 倍；同一天沿同一有向边移动的 K 名玩家各消耗
  `2K` 倍。沙暴日禁止移动，但允许在矿山原地挖矿。
- 同矿收益为每人 `R/K`，挖矿消耗仍为 3 倍而不是 `3K` 倍。
- 村庄只有实际购买者计入人数；单人购买按 2 倍基准价，多人同村同日购买按 4 倍。
- 玩家进入矿山当天不能挖矿。到达终点后退出后续互动。
- 未到终点的日末水、食物必须各不少于 1 箱；到达终点当天允许恰好为 0。
- 终端财富为现金加剩余水、食物按基准价一半计算的清算价值。
- 所有整数状态守恒残差必须精确为 0；混合均衡浮点计算容差使用 `1e-8`。

## 工程结构

两个子问均保持与第一、第二问一致的独立单元结构：

```text
求解代码/第三问（k）/
├── 模型求解/
├── tests/
├── 结果输出/
└── 结果验证/
```

两个目录不跨目录导入彼此代码，也不修改第二问模块。它们使用相同的公共接口命名，
但各自保留与本关信息结构相适配的实现，避免第五关的开环假设渗入第六关在线策略。

## 第三问（1）：第五关开环有限动态博弈

### 模块职责

- `config.py`：游戏参数、第五关 13 节点 25 条无向边、天气和关键节点。
- `data_loader.py`：构造配置并验证边唯一性、对称邻接、连通性和关键节点可达性。
- `transition.py`：状态、动作、完整计划记录和唯一的多人逐日转移内核。
- `single_dp.py`：固定对手完整计划后的 Pareto 标签 DP 最优响应 Oracle。
- `game_open_loop.py`：单人最优初始化、轮流最优响应、循环检测、候选均衡保存、
  纯 Nash 搜索和受限策略集上的两人混合均衡求解。
- `validator.py`：独立逐日复算、全局单边偏离、更新顺序与初始策略稳健性检验。
- `sensitivity.py`：对 R、M、C0 和更新顺序执行离散阈值扫描，记录策略变点。
- `export.py`：保存玩家逐日记录、求解摘要、均衡检验和灵敏度表。
- `run.py`：组织求解、检验和输出；任何检验失败时返回非零状态。

### DP 与均衡搜索

最优响应状态使用 `(day, node, water, food)` 的 Pareto 标签，现金作为标签价值而不是
额外离散维度。固定对手计划后，将对手在各日的有向边、矿山行为转换成时变外部性；
每个候选计划必须由完整 DP 产生，不在人工路线集合内局部挑选。

轮流最优响应以忽略对手时的单人最优计划为初值，并支持两种玩家更新顺序。候选策略
稳定后，对每名玩家重新调用全局 DP Oracle，计算
`epsilon_i = BR财富 - 当前财富`。只有全部 `epsilon_i = 0` 才标记为纯 Nash。
若最优响应发生循环，则在已生成策略构成的两人受限博弈上求混合均衡，并继续调用全局
Oracle 扩展策略集；只有支持内无盈利偏离且支持外 epsilon 不超过 `1e-8` 时才通过。

### 第五关输出

- 两名玩家的初始采购、逐日节点/动作/库存/现金、到达日和终端财富。
- 逐玩家偏离收益、总体 epsilon、路线重合率、同向边冲突和同矿事件。
- 不同更新顺序、初始分支和参数扫描下的均衡分支与策略变点。

## 第三问（2）：第六关滚动鲁棒阶段博弈

### 模块职责

- `config.py`：游戏参数、5×5 网格 25 节点图、村庄 14、矿山 18、终点 25。
- `data_loader.py`：生成网格边并执行与第五关相同的图审计。
- `transition.py`：三人联合转移；精确处理同向移动、同矿收益和同村购买。
- `robust_value.py`：以剩余天数和沙暴预算 Gamma 为状态的单人鲁棒续值 Oracle；
  使用 Pareto 支配和最短距离下界剪枝。
- `game_rolling.py`：合法单日动作生成、联合动作支付、纯阶段 Nash 枚举、每日滚动。
- `baselines.py`：B0 最短可行路、B1 独立鲁棒 DP、B2 短视阶段博弈。
- `validator.py`：独立守恒审计、同前缀反事实信息泄漏检验、逐日 exploitability、
  冲突损失和 Ex-post regret。
- `validation_experiments.py`：Gamma、R、M、C0、n 扫描、消融实验和小规模精确对照。
- `export.py`：保存逐日轨迹、均衡、审计、基准、消融、灵敏度及精确对照数据。
- `run.py`：提供可配置天气轨迹的离线复现实验入口，同时保持策略接口在线合规。

### 在线接口和天气边界

核心接口形式为：

```python
choose_actions(day, current_weather, public_states, gamma_remaining, config)
```

该接口不接受完整天气数组。完整天气轨迹只由外围模拟器逐日揭示当前元素；验证器用两条
具有相同历史前缀、不同未来后缀的轨迹调用策略，要求当前动作和支付张量完全一致。

第 0 天初始采购由不读取未来真实天气的 Gamma 预算单人鲁棒规划确定。起点采购不属于
题目规定的村庄多人加价事件，因此三名玩家分别建账并按基准价采购；采购后立即检查现金
和负重。外围模拟器随后从第 1 天开始逐日揭示天气并调用在线接口。

Gamma 是情景变量，不声明为真实沙暴上限。`Gamma=6` 仅作为同题已知历史序列的经验
参考点，并与完整整数扫描结果一同输出。

### 阶段博弈

每个决策日先生成各玩家合法动作，再枚举当日联合动作。联合转移精确计算当前多人耦合；
动作后的每名玩家状态由单人鲁棒 Oracle 估计最坏续值，形成一般和博弈支付。

先保留全部纯 Nash 联合动作。存在多个纯均衡时使用确定性代表选择规则保证可复现，同时
在输出中保留均衡集合；没有纯均衡时，对三人有限阶段博弈执行混合策略数值求解，并以
实际 exploitability 复核。只有 epsilon 不超过 `1e-8` 才接受混合均衡；否则明确报错，
不把近似纯动作包装成 Nash。

### 第六关检验和输出

- 独立逐日规则审计及水、食物、资金精确守恒残差。
- 同前缀信息不变性、逐玩家/逐日 epsilon 和 `epsilon_max`。
- B0/B1/B2/Full 在同一天气情景下的成功率、财富和冲突损失。
- 移动、矿山、村庄三类冲突损失及总 `L_conflict`。
- 给定事后天气与对手真实轨迹的单玩家 Oracle 和 Ex-post regret。
- 小图短期精确联合动态博弈对照的价值差与动作一致率。
- Gamma、R、M、C0、n 的扫描结果及策略变点；n 扫描明确标为推广试验。

## 测试策略

采用测试驱动开发，生产代码前先建立失败测试并确认失败原因正确。测试至少覆盖：

1. 第五关 13 个节点、25 条唯一无向边及指定关键节点；第六关 5×5 网格 40 条边。
2. 图对称性、连通性、起点到矿山/村庄/终点可达。
3. 同向移动按有向边计数；反向移动不合并；倍率为 `2K`。
4. 同矿收入 `R/K` 且消耗固定 3 倍；同村仅购买者计数并采用 2/4 倍价格。
5. 沙暴禁行、到矿当天禁挖、终点退出、库存/现金/负重约束及半价清算。
6. 第五关 DP 与可穷举缩小实例一致；候选均衡的全局偏离为 0。
7. 第六关相同公开前缀下当前决策不受未来后缀影响；纯阶段均衡逐日 epsilon 为 0。
8. 鲁棒值随 Gamma 增大不应改善；小规模近似/精确对照输出字段完整。
9. 导出文件使用 UTF-8-SIG CSV 和 UTF-8 JSON，重复运行结果可复现。
